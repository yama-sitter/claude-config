# テストガイドライン（日本語ミラー）

> **このファイルは人間用のミラーです。** Claude は英語正本 (`test-guidelines.md`) を読みます。

## テストを書く前に

- 同じディレクトリまたは機能の既存テストを 2-3 個読んで、規約・ヘルパー・ファクトリを把握する
- 既存のテストヘルパーを再利用する — 同等のものがある場合は新規作成しない

## 期待値

期待値はプロダクションコードから独立していなければならない。

❌ `assert result == width + height + PADDING * 2`（プロダクションの数式を複製）  
✅ `assert result == 524`（手動計算でハードコード）

> **Rationale**: プロダクションの数式にバグがある場合、テストが同じバグをコピーしてしまう。期待値を独立させることで、プロダクションコードの変更がテストを適切に失敗させられる。

## モック

外部境界（API コール、ネットワーク、ファイル I/O、タイマー、外部サービス）のみモックする。

以下はモックしない：

- シンプルな述語や型チェック
- 内部の純粋関数やユーティリティ関数
- テストケースが一切実行しない関数
- 実際の実装でコンストラクトできるオブジェクト

## 禁止パターン

- コンパイラや型システムがすでに保証していることのテスト（戻り型、インターフェース準拠など）
- 実装の詳細のテスト（内部状態の形状、プライベートメソッドの呼び出し）
- 具体的な値が期待できる場面でゆるいアサーションを使う
- テストシナリオで一切呼ばれないモジュールのモック/スタブを作成する

## 構造

- Arrange / Act / Assert を空行で分ける
- 1テストケース、1ビヘイビア
- 関数/メソッドまたはシナリオでグループ化する
- テスト名は期待される動作と条件を記述する

## 検証のためのテスト選択

- キーワードの類似性だけでテストを選択しない。テストは変更されたコードパスを実際に実行するものでなければならない
  - 悪い例：コンポーネントの JSX レイアウトを変更 → 同じ機能ディレクトリのフックテストを実行
  - 良い例：コンポーネントの JSX レイアウトを変更 → そのコンポーネントをレンダリングする親コンポーネントの統合テストを実行

- 変更されたファイルに直接のテストファイルがない場合は、常にインポートチェーンを辿ってカバーするテストを見つける：
  1. 変更されたファイルをインポートするテストファイルを検索する
  2. 見つからない場合は、変更されたファイルを実行する親モジュールをインポートするテストファイルを検索する
  3. カバーするテストが存在しない場合は、テストを実行するのではなくこのギャップをユーザーに報告する

> **Rationale**: 関係ないテストをパスさせても変更の正しさの証明にならない。インポートチェーンを辿ることで、実際に変更コードを通過するテストを確実に特定できる。
