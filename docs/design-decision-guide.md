# 設計判断ガイド

> 出典: kawasima 氏「Decision Quality と設計判断失敗パターン」(2026-05-07 取得)。
> agent-memory に原文併存（`~/.agent-memory/general/2026-05-07_decision-quality-design-failure-patterns/document.md`）。本ファイルが LLM 参照用の真の source。

このガイドは LLM が plan 作成 / brainstorm 対話で参照することを目的とする。設計判断の質を高めるための 3 層構造で構成される。

1. **DQ 6 要素**: 思考プロセスのフレーム
2. **8 評価軸**: 設計の妥当性を測る軸
3. **16 失敗パターン**: 陥りがちな失敗とその回避指針

LLM は plan / brainstorm 中、該当する層を参照して自己点検すること。

---

## 1. Decision Quality 6 要素（思考フレーム）

設計判断の品質を評価する 6 要素。判断プロセスをこの 6 つで点検する。

- **Frame**: 何を解く問題か。範囲・前提・制約を明確にする。
- **Alternatives**: 選択肢を最低 2 つ用意する。1 案しか出ていないなら検討不足。
- **Information**: 判断根拠となる情報の質と量を確認する。
- **Values**: 何を優先するか（速度 / 信頼性 / 拡張性 / コスト等）を明示する。
- **Sound Reasoning**: 情報から結論への論理的整合を確認する。
- **Commitment to Action**: 決定から実行への移行とコミット。「決めて動く」段階を曖昧にしない。

**使い方**: brainstorm 対話の Step 3 でこの 6 要素を質問の網として使う。漏れている観点は追加質問で埋める。

### 1.1 トリガー質問例（brainstorm Step 3 で使える具体質問）

| 要素 | 質問例 |
|---|---|
| Frame | この問題の境界はどこか。何を含めて、何を含めないか |
| Alternatives | 他にどんなアプローチがあり得るか。最低 2 つ挙げる |
| Information | この判断に必要な情報は揃っているか。欠けているものはあるか |
| Values | 速度 / 信頼性 / 拡張性 / コストのうち何を優先するか。トレードオフは |
| Sound Reasoning | 集めた情報から結論に至る論理を説明できるか |
| Commitment to Action | いつまでに何を決め、誰がどの範囲を担当するか |

## 2. 8 評価軸

設計判断を評価する 8 軸。各軸の問いに答えられるかで設計の妥当性を測る。

| 軸 | 問い |
|---|---|
| 目的適合性 | 解こうとする問題そのものに合致しているか |
| 制約適合性 | 既知の制約（時間 / 金 / 人 / 技術）に収まっているか |
| 実現可能性 | 現有リソース・スキルで実装できるか |
| 品質要塞 | 求められる品質水準（信頼性 / 性能 / 保守性）を満たすか |
| 時間効果 | 時間あたりの効果が見合うか |
| リスク・不確実性 | リスクが許容可能か。不確実性は管理可能か |
| 整合性 | 既存設計・チーム方針・組織方針と整合するか |
| 含意可能性 | この決定の波及（他の判断・将来の選択肢）が許容範囲か |

**使い方**: 提案 / Approach を立てたあと、この 8 軸を順に当てて「答えられるか」を点検する。答えに窮する軸が支配軸（その判断で最も重要な軸）の可能性が高い。

## 3. 16 失敗パターン

設計判断で陥りがちな失敗。各パターンは「兆候 → 回避指針」の形で記述。3 系統に分類する。

- **取り過ぎ系（過剰設計）**: 必要以上に作り込む / 守る
- **取り足りない系（場当たり）**: 検証や情報が足りないまま進める
- **整合性失敗系**: 既存・周辺・所有境界との齟齬

### 3.1 取り過ぎ系（過剰設計）

- **車輪の再発明**: 既存ライブラリ / 機能を見ずに自作している。回避: 候補を一度は調査してから自作可否を判断。
- **牛刀をもって鶏を割く**: 課題規模に対し過剰な道具立てになっている。回避: 小さく始めて足りなければ追加。
- **身の丈に合わない設計**: チーム / 組織の運用能力を超えた設計。回避: 運用主体の能力を起点に設計。
- **羹に懲りて膾を吹く**: 過去失敗への過剰な防御で設計が歪む。回避: 過去失敗の確率と影響を再評価し、必要分だけ防御する。
- **早すぎる抽象化**: 1 ユースケースしかないのに抽象化を導入。回避: 3 ユースケース目までは具体実装で待つ。
- **取らぬ狸の拡張点**: 来ない拡張要求のための拡張点を仕込む。回避: YAGNI。具体要求が来てから拡張点を追加。

### 3.2 取り足りない系（場当たり）

- **場当たり対応**: 過去判断と整合しない場面ごとの対応をしている。回避: 既存の判断系列を見渡してから対応方針を決める。
- **早合点**: 不十分な情報で決定している。回避: 判断に必要な情報の有無を最初に確認する。
- **見切り発車**: 検証不十分のまま実装着手。回避: 仮説の検証を実装の前に終わらせる。

### 3.3 整合性失敗系

- **制約の後付け**: 既知の制約を Approach に織り込んでいない。回避: 制約を最初に明示し、Approach の前提に含める。
- **過去への忖度**: 既存設計への過剰配慮で設計が歪む。回避: 過去設計の価値を再評価し、変更コストと比較。
- **名ばかりの完了**: 動くだけで品質要件未達。回避: 完了の定義を品質込みで設定。
- **越境実装**: 本来別所有の領域を侵食している。回避: 所有境界を確認し、越境が必要なら明示的に交渉。
- **鄕に従わば正論**: 文脈無視の正論を持ち出している。回避: その文脈で本当に正しいかを問う。
- **隣を見ない再実装**: 同等機能が隣接モジュールにあるのに再実装。回避: 隣接コード / モジュールを必ず確認。
- **砂上の依存**: 信頼性が不明な依存先を前提にしている。回避: 依存先の信頼性（メンテ状態 / 実績 / 代替）を事前評価。

**使い方**: plan の Risks セクションを書くとき、この 16 パターンを当ててみて該当するものがあれば Risks に転記する。

### 3.4 パターン × 欠けがちな DQ 要素

各失敗パターンが特に欠けている DQ 要素を示す。複数を同時に欠くパターンもある。回避指針が浮かばないときは、対応する DQ 要素を補強する方向で考えると糸口が掴める。

| パターン | 欠けがちな DQ 要素 |
|---|---|
| 車輪の再発明 | Information |
| 牛刀をもって鶏を割く | Values（時間効果軸を軽視） |
| 身の丈に合わない設計 | Frame（運用主体の能力範囲） |
| 羹に懲りて膾を吹く | Values（過去失敗の重みづけ） |
| 早すぎる抽象化 | Information（具体例不足） |
| 取らぬ狸の拡張点 | Information（拡張要求の証拠不足） |
| 場当たり対応 | Frame（既存判断との関係） |
| 早合点 | Information |
| 見切り発車 | Information / Sound Reasoning |
| 制約の後付け | Frame |
| 過去への忖度 | Values（変更コストの重みづけ） |
| 名ばかりの完了 | Frame（完了の定義） |
| 越境実装 | Frame（所有境界） |
| 鄕に従わば正論 | Frame（文脈把握） |
| 隣を見ない再実装 | Information |
| 砂上の依存 | Information（依存先信頼性） |
